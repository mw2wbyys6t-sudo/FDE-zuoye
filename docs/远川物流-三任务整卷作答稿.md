## 任务1 开启角色访谈

### 1.1 开始角色访谈（会话设置）

**会话形式**：一对一异步文字访谈，六个角色分别进行，不合并、不交叉。每个角色两轮：第一轮开放问「请讲实际流程」，第二轮按异常事件逐项追问。这样做的原因是角色之间存在责任分歧（仓库按出库算完成、配送站按正确收货算完成），合访会让一方替另一方回答。

**会话参与者**：

| 角色 | 在本次调查中的位置 | 选择理由 |
|---|---|---|
| 顾明岚 · 仓储经理 | Buyer（发起人） | 定范围、定节奏、确认预算，唯一能给出目标值的人 |
| 林亦舟 · 拣货员 | Operator（一线） | 唯一能还原错误发生现场与绕行习惯的人 |
| 唐映秋 · 波次计划员 | 流程与交接责任人 | 负责异常分派、交接五要素、退回原因 |
| 秦芮 · WMS 工程师 | 技术与数据责任人 | 决定主编号、字段映射、接口与延迟是否可做 |
| 傅景 · 仓库安全主管 | 审批者 / 否决者 | 安全红线、审批留痕、验收停止条件的唯一否决权 |
| 叶书 · 配送站长 | 下游验收方 | 客户侧口径、争议受理、回传闭环 |

未访谈财务角色：22 万元预算由顾明岚确认，但预算科目、审批层级、付款主体无证据，出资者目前无人认领。**[待核实]**

**访谈目标**：
1. 还原最近一次具体异常事件的完整时间线（起止节点、损害何时被谁看见）。
2. 区分客户提出的功能（AI 防错提示）与真正要改善的业务结果。
3. 界定范围、权限与安全红线，确认谁能否决。
4. 确认验收口径、停止条件与决策链，判断当前证据是否足以立项。

**需要采集的访谈结果**：主流程与节点责任、最近一次异常样本、指标现状值与分母口径、各节点耗时是否分别测量、系统与字段现状（主编号/编码/延迟）、审批矩阵与账号边界、验收与停止条件、留存与审计要求。

**推进方式**：按流程顺序访谈（决策者 → 一线 → 流程 → 数据 → 安全 → 下游），每个角色固定六问——实际流程、数据字段与质量、审批与权限、最费时间的环节、一个具体失败例子、验收与红线。角色回答「尚未核实」时原样记录、不替其推演；每轮结束回填事实台账（编号 + 来源文件 + 版本 + 样本时间窗），共采集 36 条事实（f00–f55）。

---

### 1.2 访谈方法论

**问了谁、怎么定的**：先用主流程锁定责任人（订单归集 → 波次分配 → 拣选 → 复核 → 集货 → 装车扫码），再按三个条件补人——谁能决定范围与预算（顾明岚）、谁能否决上线（傅景）、谁承担下游结果（叶书）；技术可行性补秦芮，失败现场补林亦舟。这样六个人刚好覆盖「决定权、执行点、数据、否决权、验收方」五类信息，不重复也不遗漏。

**问了什么**：每个角色都走同一条问题链——① 现在的实际流程是什么、这一步的输入输出与待办责任人是谁；② 数据有哪些字段、口径或质量问题；③ 哪些操作必须人工审批、谁有权限；④ 日常最费时间的是哪一段；⑤ 给我一个具体的异常或失败例子；⑥ 怎么验收、哪些是红线、记录留多久。追问只追两件事：这个数字有没有记录、谁出数；这件事是你确认的，还是你推测的。

**拿到了什么**：36 条可引用事实。关键几条——f01 六节点从未分节点计时；f11 取消单已进波次、拣完仍被装车、到站才发现；f31 取消事件同步延迟 12 分钟、短拣原因编码不一致；f30/f33 三系统账号独立、状态无统一视图、歧义记录须进人工修复队列；f41/f42/f44 权限与账号红线、验收双硬线、转人工三要素；f50/f53 出库与正确收货两套完成口径；f10/f14 相似包装错拿与便签/群说明不随单。

**如何处理拿不到的信息**：把回答分成四级——事实级（角色明确确认）、估计级（有数无口径）、推算级（我用估计值推的量级）、待定级（角色本人说尚未核实）。待定项一律留在问题清单里，不用推测补齐，也不替未访谈角色编造陈述，因此任务1交付的是「机会清单 + 验证路径」，不是已选定的功能方案。

### 1.3 四来源收敛与材料核对

**Buyer · 顾明岚（已采集角色陈述）**：目标为错发率 1.8%→0.5%、装车复核 35→20 分钟（f00，管理层目标，口径未定）；首期预算 22 万元，收益须扣除维护与人工复核成本（f03）；可定试点范围与节奏，首期限定只做扫码解释与错配提醒、先历史回放再小范围并行（f05）；但安全红线否决权不在其手（f04）。

**Brief · 书面需求（缺位）**：现有材料只有场景开场诉求——相似包装 SKU 相邻货位、新员工常拿错、管理层想用 AI 改善，但未定优先环节、验收标准与权限边界。**书面 Brief 原文与版本待补**，不能把开场诉求当作已批准的立项书。

**Industry · 行业可行性（缺位）**：需要可比技术案例、同类仓内拣选的数据条件与接口能力核验。企业业务介绍不能证明技术可行，本项暂无证据，**待补**；因此本次不引用任何行业效果数字做承诺。

**Operator · 林亦舟（已采集现场陈述）**：错拿发生在相似包装相邻货位（f10）；真实操作知识留在个人便签与群消息、不随单据交接（f14）；每日 7000 行拣选、人工重复复核约 14 人时（f12）；取消单在拣选时看不出状态变化（f11）；高峰只能用现有终端、不能离场补录（f13）。

**收敛结论**：
- **已收敛（三方一致）**：问题出在节点之间的信息交接，而非单点能力不足。一线给出失败位置（拣选错拿、装车漏判），流程方给出交接规则失效（仅发消息不算完成，f23），下游给出后果（到站才发现、客户解释，f50），三者指向同一条链。
- **未收敛（保留分歧）**：Brief 与 Industry 两个来源缺位，无法确认范围授权与行业可行性；拣选与装车对错发的贡献占比无分解数据，**不能认定拣选是主因**。
- **差异记录**：顾明岚看指标与工时，林亦舟看手边提示与不增加填报负担，叶书看客户是否拿到正确货，傅景看规程与留痕。目标表述不同，但都要求「状态在装车前可见」——这一点可作为最小共识。

**据此形成的候选需求（6 条，均为待验证假设）**：O1 拣选相似包装 SKU 防错提示；O2 取消单在波次与装车之间的拦截点；O3 跨系统主编号与状态口径治理；O4 分节点基线与装车复核耗时压缩；O5 错发率与复核漏扫口径固定；O6 人工兜底与审批矩阵成文。

### 2.2 哪些数字只是估计

- **事实级**（角色明确陈述，仍需日志或制度文件交叉验证）：取消同步延迟 12 分钟、每日两次状态更新与「待刷新」规则、22 万元预算、90 天留存、权限与账号规则、版本冲突处理规则、三系统状态不统一、短拣原因编码不一致。
- **估计级**（有数、无分母、无周期、无出数人）：1.8%/0.5%、35→20 分钟、7000 行/日、14 人时/日。35 分钟尤其未分节点，属「凭现场感受」。
- **推算级**（以估计值作分母的量级推算，分母一改即失效）：约 126 行/日 → 35 行/日、差约 91 行/日、1.3 万行/月；14 人时 ≈ 1.75 人日。**仅用于说明损失量级，不得写入验收材料。**
- **待定级**：错发率分子分母、漏扫定义与现状值、35 分钟节点构成、可节省工时、主编号可关联比例、交接完成率、分节点计时基线。

### 2.3 三个必须先解决的口径冲突

1. **完成口径分歧**（f50/f53）：仓库按出库算完成，配送站按正确收货算完成。处理：基线表双列并行（仓内视角 / 站点视角各一列），取消单单独一栏，不做合并。
2. **重复计数风险**（f53）：同一业务可能被拆成多次「成功」。处理：以业务编号为唯一计数键，一个业务编号在一个周期内只计一次。
3. **编码与主编号不一致**（f30/f31）：短拣原因编码不一致、三系统主编号独立。处理：歧义记录进人工修复队列，不进入自动推荐样本；先统计可自动关联比例，再定接口范围。

### 2.5 仍待核实

1. 错发率分子按单还是按行？分母用仓内出库单还是站点正确收货单？取消单是否剔除？统计周期多长？**五问须书面回答，缺一则数字不可用。**
2. 「复核漏扫」的判定定义、判定人、依据哪条记录。
3. 35 分钟 / 20 分钟统计哪类装车、单量多少、是否含等待。
4. 14 人时/日折算到复核岗位工时，还是试点期额外人手。
5. 并行运行期间原流程不撤，重复投入是否计入成本（需财务确认）。
6. 「待刷新」在拣选与装车核验中只提示还是阻断（秦芮只能给状态标识，不能自定拦截口径）。

### 3.2 决策链与升级路径

- **立项 / 范围 / 节奏**：顾明岚决定，傅景（安全）、叶书（验收口径）会签（f04）。
- **安全红线与上线否决**：傅景唯一否决权；触及停止条件即暂停试点并由负责人复盘（f42）。
- **异常分派与升级**：唐映秋分派给实际处理人，超时升级顾明岚；跨岗必须写明下一责任人，不能只写「已转交」（f25）。
- **规则版本冲突**：傅景裁定，唐映秋附两个版本，不自行合并、不选宽松条款（f24）。
- **客户投诉与争议**：叶书受理、唐映秋核对，先关联原业务编号与当时资料版本（f54）。
- **货位与库存变更**：主管批准，秦芮只出提示不落库（f32）。
- **验收结论**：顾明岚（口径）+ 叶书（服务结果），傅景复核审计材料与红线（f42）。
- **审批矩阵（拣选差异放行、装车核验异常关闭）**：**未核实，是当前决策链最大缺口**，直接阻断「谁批准继续或停止」的闭环，须顾明岚与傅景在 G2 前补齐。

### 3.4 调查边界与授权

**已获授权 / 明确边界**：
1. 只读核对与人工交接；合成训练不代表真实授权、业务执行或客户验收，不预设根因、预算或承诺收益。
2. 仅授权业务岗位可查看 SKU 图片、货位表、波次、复核与装车事件，不得借用他人账号（f41）。
3. 秦芮仅可读波次与扫码事件，调整货位与库存须主管批准（f32）。
4. 只做扫码解释与错配提醒，不自动操作叉车、不做盘盈盘亏（f05/f52）。
5. 审计不记账号口令与不必要个人信息（f45）；原始资料按本场景授权范围保存（f43）。
6. 取消单已进波次、资料缺依据、版本冲突、系统不可用 → 转人工并标注触发原因、接手人、确认时间（f44）。

**仍需取得的授权**：访谈录音/引用授权与脱敏范围（**尚未取得**）；历史回放资料的调取授权与提供人（顾明岚已追问，无人认领）；留存期限的组织规则；预算科目与出资方；客户侧对合成场景的正式确认。

## 附：三任务结论一句话版

- **任务1**：异常事件是「取消单已进波次、拣完仍装车、到站才发现」；客户提出的是防错提示（手段），真正要的是错发率、漏扫、复核时长、取消单外溢四条结果，且拣选与装车的贡献尚未分解，故先交机会清单与验证路径。
- **任务2**：所有关键数字里只有 12 分钟延迟、22 万预算、90 天留存、每日两次更新是事实；1.8%、35 分钟、7000 行、14 人时全部是估计，必须先固定分母、周期与出数人，再做两周分节点计时。
- **任务3**：顾明岚发起、傅景否决、叶书验收、唐映秋处置、秦芮供数、林亦舟反馈；出资者缺位、审批矩阵未定，这两项不补齐就不具备立项条件。
